# Integrated operations frontend

Verified locally on 5 October 2026, on `post-competition/integrated-local-backend`. These are post-competition changes, not changes attributed to the original submission.

## What is connected

The existing React/Vite application now has a separate `operations.html` entry. Its overview lists actual saved workflows and supports unit/order search and route/manager/state filters. Workflow detail shows expected order lines, independent execution states and business verdicts, manager findings, human reviews, evidence and audit history. Receiving branches to Prep for FBA or Pack for merchant/3PL; absent event-driven Returns/Recovery stages are explicitly not scheduled.

Operators can register products and units, start workflows and upload evidence. Backend eligibility controls route correction, hold/resume/cancel, event registration, retry and supervisor review. Review requires evidence, capture time, findings and a reason, followed by confirmation. Actor identity comes from authentication. Original findings remain visible. Stale conflicts preserve the draft and require loading the current version.

The integrated backend's automatic visual adapters remain BLOCKED. Uploaded images are not automatically inspected. No observed product list or count is invented, and Recovery cannot approve or submit claims. Synthetic test records and manual findings carry explicit labels.

```powershell

```

Open http://127.0.0.1:5173/operations.html. Choose the private `.local/integrated-client.json` account file generated by `python -m backend.integrated.dev init`. The browser reads the file locally; it sends the token only in the Authorization header to the local API proxy. Alternatively enter the token locally in the password field. Do not share or commit the file/token. Memory-only authentication is the default. The optional tab-session checkbox enables sessionStorage so a refresh can restore the session; disconnect clears it.

Frontend `.env.example` documents `INTEGRATED_API_TARGET`. It defaults to the verified http://127.0.0.1:8010 and accepts loopback HTTP addresses only. It is a Vite server setting, not a client credential. The UI uses `/operations-api` through this proxy. The existing `/api` proxy and Pack entry remain intact. Standalone static hosting/preview does not provide this development proxy; no deployment was configured.

## Actual API calls

Every business request is authenticated. Mutations have an Idempotency-Key; the server still validates roles, tenant, versions and workflow eligibility.

| Method | Endpoint | Interface use |
|---|---|---|
| GET | `/v1/session` | Verified operator, role, inference state, manual check registry and upload limits |
| GET/POST | `/v1/catalogue` | Product list and explicit product registration |
| GET/POST | `/v1/units` | Unit/order lookup and registration |
| GET/POST | `/v1/workflows` | Overview and workflow start |
| GET | `/v1/runs` | Review queue and filtering |
| GET | `/v1/workflows/{id}/context` | Unit, workflow, runs, audit, redacted image metadata and allowed actions |
| GET | `/v1/images/{id}` | Private image bytes after authorization |
| POST | `/v1/workflows/{id}/images` | Validated multipart upload with progress |
| POST | `/v1/runs/{id}/review` | Attributed manual review with expected version |
| POST | `/v1/runs/{id}/retry` | Only backend-eligible retry |
| POST | `/v1/workflows/{id}/control` | Hold, resume or cancel |
| POST | `/v1/workflows/{id}/route` | Resolve an unknown route with source and reason |
| POST | `/v1/workflows/{id}/events` | Explicit return or charge event |

The only added backend routes are the read-only session/context endpoints. They reuse review/retry eligibility checks from the mutation paths and return no filesystem keys. Existing mutation authorization remains authoritative.

## Reliability and data storage

There is **one shared local PostgreSQL database**, not one database per manager. `cw_runs` holds Receiving, Prep, Pack, Returns and Recovery outputs linked to organization/workflow/unit. `cw_workflows` and `cw_units` hold shared context, `cw_events` preserves attributed events, `cw_requests` handles idempotency and `cw_calls` preserves call-budget reservations. Original Pack tables remain in the same database. Image metadata is stored in `records`; image bytes remain in local private storage. Tenant RLS and authorized image access apply.

The typed client validates read responses, shows stable server error codes and has bounded request timeouts. It does not automatically retry mutations. Concurrent duplicate submissions are suppressed; after an ambiguous failure, a manually repeated identical request reuses its in-memory idempotency key. Backend deduplication and version checks still apply. Changing/reloading the browser does not reset backend budgets. Context refresh failures visibly mark stale data and disable actions. Review drafts warn before dismissal/navigation. Private images are fetched with authorization into revocable blob URLs.

## Remaining limitations

- Automatic recognition/counting, authoritative channel-rule adapters and claim eligibility are unavailable in this integrated service. It is a durable manual operations workflow.
- Physical phone camera hardware was not exercised. Browser layout and capture-input behavior were checked; loopback hosting is accessible only on this computer.
- Local bearer authentication is development authentication, not deployed identity management. No cloud service, public URL or hosted inference was added.
- The build reports the existing large Pack bundle and third-party annotation warnings; compilation succeeds.
- Software tests do not establish image interpretation accuracy or competition eligibility. Original research results and submission limitations remain unchanged.
